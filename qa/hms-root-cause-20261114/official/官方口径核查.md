# Android Wear Engine / HiWear：非华为手机与 HMS Core 官方口径核查

> 调研日期：2026-11-14，CST（UTC+08:00）。本次仅访问公开资料并在指定 `official/` 目录保存证据；没有下载 APK、安装 App、改变手机设置、登录账号、写控制台、执行 ADB 或启动／控制浏览器。
>
> **这是官方条件核查，不是本次故障的因果定论。不能写“装 HMS 必好”，也不能写“LSPatch 改包已证实是根因”。**

## 一、结论先行

1. **Android 手机侧 Wear Engine / HiWear 明确支持非华为 Android 手机，不是仅限 HarmonyOS 手机的 `@kit.WearEngine`，也不是 Google Wear OS。** 官方 Android Java 参考把 `HiWear` 定义为 Wear Engine 功能总入口。官方设备表列“Other phones：Android 6.0–14.0”；入门页列 Android 6.0 及以上、`minSdkVersion 23`、`compileSdkVersion 34`。后两项是应用构建条件，不意味着手机必须 Android 14。[S01–S03、S17]
2. **对非华为手机，Wear Engine 专属中英文入门页均明确要求同时装有 HMS Core（APK）和华为运动健康。** 中文还明确要求允许运动健康“在后台弹出界面”；英文表述为允许运动健康在后台运行。两种后台表述应分别保留，不能互相当作同一权限。[S01、S02]
3. **Wear Engine 专属 HMS Core 最低版本：本次覆盖的官方一手正文未明示／未查到公布值，不能给出具体数字。** 这不证明没有版本限制，更不表示任意旧版都可用。官方通用支持建议安装／更新到可获得的最新版本，而不是公布 Wear Engine 的固定最低号。[S01–S03、S10、S16]
4. **当前运动健康的系统条件要与 Wear Engine 的基础条件分层看。** 华为运动健康下载支持页目前写 Android 8.0 及以上；因此不能只凭 Wear Engine 的 Android 6.0 基线，宣称今天最新版运动健康仍支持 Android 6/7。Wear Engine 设备表明确列到 Android 14，也不能据“6.0 及以上”无限外推到 Android 15/16。[S03、S08]
5. **可信安装入口已由完整官方正文确认：设备原生应用商店搜索 HMS Core；找不到则使用华为应用市场 App；仍找不到客户端则从华为官方 AppGallery 网页进入。** 本次只核查入口，未获取／验证具体 APK 的版本、大小或签名。[S05、S06、S11、S19]
6. **此次因果仍未定。** 父代理实证已表明运动健康 Service 第一段绑定成功，HMS 缺失未阻止这一段；但这不能证明后续 AuthManager、Scope、用户授权或 P2P 均成功。缺 HMS 是与专属指南不一致的环境条件，不是已经证明的故障根因。

S07：<https://consumer.huawei.com/cn/support/content/zh-cn15841699/>

同页还写：

## 五、对小米的合理副作用边界

以下分为“官方事实”和“有依据的工程判断”，不作小米 Mi 10 Pro 的零风险承诺。

### 1. 不是把小米变成华为，也不是 GMS 替代品

S05 的消费者路径是普通 App／应用市场安装，没有要求 root、刷机、替换系统或卸载 Google 服务。S09 <https://consumer.huawei.com/en/support/content/en-us15841718/> 原文：

> Just like GMS Core (Google Mobile Services), HMS Core can run on the Android Open Source Project (Android system) and supports Android apps. However, certain Android apps require support from GMS Core and may not be able to run on HMS Core.

**工程边界：**应把它视为增加华为基础服务及其依赖，而非替换小米系统或补齐所有 Google 功能。没有证据要求为本次 Wear Engine 使用删除 GMS；同样，不能凭这一介绍保证本机所有 App 与所有 HMS 版本绝无冲突。部分华为服务／设备专属功能也不会仅因安装 HMS 就在小米上完整出现。

### 2. 合理可预期成本：空间、运行资源、网络、更新与账号／协议交互

- 额外 APK、数据／缓存、服务运行和更新会有存储及资源成本；选择后台保护后可能增加驻留、唤醒或耗电。**本次没有安装／测量，因此不提供耗电百分比、内存大小或“完全不影响续航”的保证。**
- S10 <https://consumer.huawei.com/en/support/content/en-us15841698/> 建议最新版本，提供手动更新及 Wi-Fi 自动更新说明。其具体设置步骤以 EMUI 为例，不能直接冒充小米 MIUI 的实机菜单，也不表示本次同意自动更新。
- 账号、隐私协议及某些功能权限可能需要用户主动确认；提供基础服务不等于必须启用云空间、支付、广告个性化、全部健康数据云同步或全部手机权限。
- 不能将 Wear Engine SDK 的“随业务 App 进程运行、关闭后不额外后台操作”声明，扩大到独立的 HMS Core APK 或运动健康 App。[S04]

### 3. 小米后台策略有官方旁证，但只限对应应用与对应场景

S12：<https://consumer.huawei.com/cn/support/content/zh-cn15981195/>

> 三方安卓手机系统管控华为运动健康App，导致推送来电和消息延迟。

该页对小米建议运动健康的省电策略“无限制”；其他品牌说明忽略电池优化、允许后台活动、自启动、锁定后台任务等。S13 <https://consumer.huawei.com/cn/support/content/zh-cn15848663/> 给出小米**运动健康**后台任务锁定方法。

Wear Engine 专属后台文档 S18 <https://developer.huawei.com/consumer/en/doc/connectivity-guides/monitoring-wearengine-service-0000001052828059> 也写：

> If the Huawei Health app stops providing services in the background (for example, due to high power consumption), your app may disconnect from Wear Engine.

**边界：**这是评估后台链路可靠性的证据，不是证明这次已经被省电策略杀死。只应在用户再次授权后按真实需要调整运动健康／HMS 的单应用设置；不应一口气关闭全机省电、安全中心、联网限制、应用扫描，或替所有 App 开无限制。S12 原故障是来电／消息延迟，也不能把其中“问题即可解决”跨场景挪成“Wear Engine 授权失败必好”。

### 4. 权限与隐私：按功能判断，不能说完全离线／不收集信息

- S14 <https://consumer.huawei.com/en/support/content/en-us15841709/> 明确 HMS Core 的权限与流量可在应用管理中查看，权限可以 Allow／Deny；步骤是 EMUI 示例，实际小米路径应由其系统界面决定。
- S04 <https://developer.huawei.com/consumer/en/doc/connectivity-Guides/sdk-data-security-0000000000019123> 说明 Wear Engine 的 Scope 鉴权需要 `android.permission.INTERNET`；SDK 设备开放能力要取得相应用户授权。因此不能把整个接入链称为完全离线的蓝牙库。
- S20 <https://developer.huawei.com/consumer/en/doc/development/hmscore-common-Guides/privacy-0000001261262707> 明确**适用于开发者服务地区为中国大陆的场景**，不同能力的数据范围／目的不同；为安全和改进会收集 HMS API 使用信息，包括设备标识、应用包名／标识、错误日志、API 时间、网络／设备／系统信息等。该声明不能被解释为“单纯安装就读取手机所有数据”，也不能凭 Wear Engine 设备信息表中的“不存储本地或云端”推出所有 HMS／运动健康业务都不联网或无数据处理。
- 不因本次课表 P2P 就默认授予联系人、短信、通用存储、无障碍或手机通知读取等无关高敏权限。必要的 SDK Scope、运动健康功能权限与 HMS 基础服务权限是不同层，不应合并成“全开”。

**可逆性边界：**官方消费者支持 S11 对三方设备给出卸载／重装 HMS 的排障步骤，但删除／停用基础服务可能使依赖它的华为登录或相关 App 功能失效；“普通 App 可卸载”不等于“无任何关联影响”。本次没有测试小米上的卸载／回滚，不建议为了试错清除现有运动健康数据或解除手表配对。

## 六、新增：官方 Android 错误码 3／7／8／9 的严格区别

主要数值证据 S25：<https://developer.huawei.com/consumer/cn/doc/connectivity-Guides/errocode-0000001054450278>，仅取其 **“手机侧：com.huawei.wearengine.common.WearEngineErrorCode”** 表，不混用同页 iOS、穿戴侧或 HarmonyOS ArkTS 的 `100850…` 码。

| 值 | 官方常量（原样） | 官方含义／层级 |
|---|---|---|
| 3 | `ERROR_CODE_HEALTH_LOGOUT` | 运动健康已安装未登录；账号登录层。 |
| 6 | `ERROR_CODE_SERVER_REMOTE_BINDER` | 服务端远端绑定对象为 null；不能自动称 HMS binder。 |
| 7 | `ERROR_CODE_USER_UNAUTHORIZED_IN_HEALTH` | 用户未同意《华为运动健康用户协议》和《关于华为运动健康与隐私的声明》；不是开发者 Scope 未批，也不是“未登录”的同义词。 |
| 8 | `ERROR_CODE_SCOPE_UNAUTHORIZED` | 未通过 Scope 权限校验；不同于用户同意／拒绝。 |
| 9 | `ERROR_CODE_USER_UNAUTHORIZED_IN_WEAR_ENGINE` | 未通过用户授权权限校验，或开发者未调用相应授权接口向用户请求授权；不能混成运动健康总协议的 7。 |
| 13 | `ERROR_CODE_DEVICE_VERSION_NOT_SUPPORT` | 设备版本不支持。 |
| 14 | `ERROR_CODE_HEALTH_VERSION_IS_LOW` | 运动健康 App 版本过低。 |
| 15 | `ERROR_CODE_HEALTH_NOT_AUTO_START` | 运动健康进程无法自启动。 |
| 18 | `ERROR_CODE_INTERFACE_IS_NOT_SUPPORTED` | 接口不支持调用。 |
| 19 | `ERROR_CODE_SERVICE_TIMEOUT` | 接口调用超时。 |

S21／S24 `WearEngineErrorCode` 类说明再次支持上述定义。S22 <https://developer.huawei.com/consumer/cn/doc/connectivity-Guides/requesting-user-authorization-0000001050819181> 明确：

> 请确保权限已在申请Wear Engine服务中审批通过，否则会遇到错误码为8的提示。

> 当用户允许后才能正常使用接口，否则会遇到错误码为9的提示。

注意第一句给的是 8 的一个具体情形，不能反过来将所有 Scope 失败都归结为“从没申请／从没批准”。用户既已确认审批通过，本次不重新复核或否定它。`checkPermission` 成功返回 `false` 与 Task 异常失败也不是同一结果；`requestPermission` 的任务执行成功与 `onOk` 中实际授予的权限列表也要区分。[S22、S23]

上述码的名称／定义没有把 7／8／9／13／15／18 定义为 HMS 专用码；但这也不证明 HMS 对后续层完全无关。**父代理尚未取得本次真实数值错误码；统一错误提示对应多个分支，只能列候选，不能由套话选定其中一个。**

## 七、本次现场事实与因果边界（父代理／用户提供，本笔记未独立复测）

| 已提供事实 | 能支持什么 | 不能支持什么 |
|---|---|---|
| 小米 Mi 10 Pro，Android 13／API 33；运动健康 `16.1.2.310`；无已装 HMS Core 包。 | Android 位于 S03 的公开区间内，满足当前 Health Android 8.0 条件；HMS 状态与 S01／S02 的专属环境条件不一致。 | 不能单靠缺包推定本次 API 失败位置或承诺安装后恢复。 |
