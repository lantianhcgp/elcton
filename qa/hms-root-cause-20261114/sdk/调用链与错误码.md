# Wear Engine 授权调用链与异常码核查

本页是从官方 AAR、已安装 elcton APK 和与已安装运动健康哈希一致的保留样本中取证的解释，不是第三方源码的完整再发布。原始 APK／DEX／完整反编译及设备日志不进入公开仓库。

## 2. 客户端：先连运动健康，不是直接连 HMS Core

`HiWear.getAuthClient(context)` → `AuthClient.checkPermission(Permission.DEVICE_MANAGER)` → Task Callable → `com.huawei.wearengine.auth.a.a(Permission)`。

`auth.a` 先初始化 AuthManager：`c.e().f()` 建立服务连接，再 `c.e().a(5)` → 服务的 `getBinder(5)` → `AuthManager.Stub.asInterface(binder)`。

`c` 对 `com.huawei.health` 创建显式 Intent，优先 `com.huawei.wearengine.service.WearEngineExtendService`，失败时回退 `com.huawei.wearengine.service.WearEngineService`；随后 `bindService` 等待连接。直接目标包不是 `com.huawei.hwid`。`com.huawei.hms.tasks` 是 SDK 的异步任务库名称，单凭包名不能说调用了独立 HMS Core APK。

SDK 在部分能力探测中还查询运动健康 ContentProvider：`content://com.huawei.healthcloud.health.provider/wear_device_state/wearEngine`。它不是 HMS Core Provider；`checkPermission` 真正的授权检查经上述 AuthManager Binder 进行，不把另一个设备能力探测接口混写成授权主体。

## 3. 服务端：第一段 Service 连接不等于鉴权已通过

从已安装运动健康同哈希样本的内层 `origin.apk`，定向反汇编以下逻辑：

1. `WearEngineExtendService` 的 `getBinder` 路径查 Health 的账号 ID；读取链是 `wts.e(context)` → `wts$4` → `wtr.e(context)` → 反射 `com.huawei.wearengine.utills.WearEngineReflectUtil.getUserId(context)` → `health.compact.a.KeyValDbManager` 的 `user_id`。这是读取 Health 本地账号记录，不是此处直接发起 HMS Binder 登录。
2. `user_id` 不满足账号校验时抛 `IllegalStateException("3")`；运动健康协议授权校验失败抛 `IllegalStateException("7")`。账号的获取／协议校验内部异常也可能影响结果，不把“能打开 Health”视为 WE 一定通过。
3. 返回 AuthManager 子 binder 之前还执行 `preGrantPermission`：校验调用应用，读 app ID／本地授权记录，必要时请求 `ScopeManager.getScope(appId,"wearEngine")` 并计算权限交集。`wqj.c(context,uid,package)` 在账号为空时返回3，app ID无效时返回12，权限交集为空时返回8；上层把非0结果包为数字字符串的 `IllegalStateException`。
4. AuthManager `checkPermission` 校验调用者与权限，再查 `AuthInfoRepository`、Scope及相关授权，成功结果是 Boolean；未授权可返回 `false`。失败与成功返回 `false` 不等价，不能一遇异常就当成尚未展示用户弹窗。
5. Scope 及账号底层可能需要网络／HMS支持。此处没有“找不到 com.huawei.hwid 就抛特定错误码”的必经分支证据；不能由直接连 Health 反推出间接完全不依赖 HMS。

## 4. SDK 怎么变成 WearEngineException

`auth.a.a(Permission)` 在已装 APK 的 smali 中已核对：

- 不支持权限 → `WearEngineException(14)`；但在此版本 `b(Permission[])` 中的额外支持探测只针对 `MOTION_SENSOR`、`WEAR_USER_STATUS`、`DEVICE_SN`，普通 `DEVICE_MANAGER` 不走该额外拒绝条件，不能把此14分支当成本次首要候选。
- AuthManager 引用为空 → `WearEngineException(6)`；初始化子 binder 空还可能报2。
- `RemoteException` → `WearEngineException(12)`。
- 捕获 `IllegalStateException` → `WearEngineException.convertIllegalStateException(e)`；该函数解析 `e.message` 数字，生成对应异常。无法解析回落到泛化码，不冒充HMS特定码。
- `WearEngineException` 持有 `errorCode`，`super(message)` 由 `WearEngineErrorCode.getErrorMsgFromCode(errorCode)` 生成。只打印类名会丢掉本来可用的数值及含义。

## 5. App 那句套话掩盖的分支

已装 `UserFacingError.explain()` 对原 message 小写后，命中 `auth`／`permission`／`not support` 就显示“Wear Engine 权限或设备能力未满足。请检查运动健康授权与服务开通状态。”

| Android SDK 码 | 原 message | 含义层级 |
|---|---|---|
| 7 | `User unauthorized in health` | 运动健康用户协议／隐私声明未授权 |
| 8 | `Scope unauthorized` | 应用服务权限、身份／Scope／缓存或网络校验未通过 |
| 9 | `User unauthorized in wear engine` | Wear Engine 特定用户权限未授予 |
| 13 | `Device version is not supported` | 设备版本／能力支持 |
| 15 | `Health does not has permission to start` | 运动健康自启动／后台启动 |
| 18 | `Interface is not supported` | 所调接口不支持 |

这些码会落入同一句话，但都不是“缺HMS”专用码。账号未登录3、Health版本低14、绑定空6／内部错误12不应仅凭套话与7/8/9混为一谈。表中精确 message 以本次SDK错误表为准，其他版本可能不同。

## 6. “从未弹窗”并不能单独定位失败阶段

已装 App 的 `authorizeAndScan()` 在 `checkPermission` 成功返回 `false` 时才 `requestPermission`；失败回调直接 `describe(e)`。成功为 `true` 则直接 `scan()`，后者调用 `DeviceClient.getCommonDevice()`，它的失败回调也用同一个 `describe(e)`。

- `checkPermission` 本来只是查询授权，不负责直接弹出用户授权界面。
- 官方版本历史明确自 SDK 5.0.1.300 配套 Health 11.0.3.512 起，可默认授予 NOTIFY 与 DEVICE_MANAGER（仍要求服务权限已批）。因此“无弹窗”甚至可以是正常预授权路径。
- `UserFacingError.diagnostic(e)` 只留 `e.javaClass.simpleName`；已装 `WearProbe.describe` 确实如此，没有 phase、errorCode、原始message、堆栈。
- 目前不能证明此次失败是 `checkPermission`、`requestPermission` 还是后续 `getCommonDevice`。用户描述的是点击动作和结果；根因报告必须保留这条可观测性边界。
